AI 코딩할 때 가장 아까운 시간이 “뭘 어떻게 물어볼지” 고민하는 시간이다.  
특히 Claude Code 프롬프트는 결과 품질을 거의 반쯤 결정한다.  
아래는 내가 실제로 자주 쓰는 **복붙용 템플릿 20개**를 상황별로 정리한 모음이다.

핵심 원칙은 단순하다.
- 역할(Role)
- 맥락(Context)
- 제약(Constraints)
- 출력 형식(Output)

이 4가지만 분명하면 AI 코딩 생산성이 확 올라간다.

## 1) 기획(Planning) 템플릿

### 템플릿 1. 기능 요구사항 정리
```text
너는 시니어 제품 엔지니어야.
아래 아이디어를 개발 가능한 기능 요구사항으로 바꿔줘.

[아이디어]
- {아이디어 입력}

[요청]
1) 사용자 스토리 5개
2) 기능 요구사항(필수/선택)
3) 비기능 요구사항(성능/보안/운영)
4) MVP 범위와 제외 범위
5) 개발 우선순위

출력은 마크다운 표 없이 불릿 리스트로.
```

### 템플릿 2. 기술 스택 의사결정
```text
너는 테크리드야.
프로젝트 조건에 맞춰 기술 스택을 3안으로 제안해줘.

[조건]
- 팀 규모: {n명}
- 기간: {기간}
- 트래픽 예상: {월간 사용자/요청량}
- 필수 요구: {요구}

[출력]
- A/B/C안 각각
  - 장점
  - 단점
  - 리스크
  - 추천 상황
- 마지막에 단일 추천안 + 이유 3가지
```

### 템플릿 3. 작업 분해(WBS)
```text
아래 기능을 1~2일 단위 작업으로 쪼개줘.

[기능]
{기능 설명}

[출력 형식]
- 작업명
- 예상 소요
- 선행 작업
- 완료 조건(테스트 가능한 기준)
```

### 템플릿 4. API 설계 초안
```text
다음 기능의 REST API 초안을 설계해줘.

[기능]
{기능}

[요청]
- 엔드포인트
- 요청/응답 JSON 예시
- 상태코드
- 에러 코드 규칙
- 인증/인가 포인트

OpenAPI 스타일로 읽기 쉽게 작성.
```

## 2) 구현(Implementation) 템플릿

### 템플릿 5. 코드 생성(파일 단위)
```text
너는 {언어/프레임워크} 시니어 개발자야.
아래 스펙으로 단일 파일 코드를 작성해줘.

[스펙]
{요구사항}

[제약]
- 외부 라이브러리: {허용/비허용}
- 성능 목표: {예: O(n log n)}
- 코드 스타일: {예: eslint airbnb}

[출력]
1) 완성 코드
2) 핵심 로직 설명 5줄 이내
```

### 템플릿 6. 기존 코드 확장
```text
아래 기존 코드를 최소 변경으로 확장해줘.

[기존 코드]
{코드}

[추가 기능]
{요구}

[중요]
- 기존 함수 시그니처 유지
- 깨질 수 있는 부분을 먼저 지적
- 변경된 라인 중심 diff 스타일로 설명
```

### 템플릿 7. 테스트 코드 동시 생성
```text
아래 구현 요구사항을 만족하는 코드 + 테스트를 같이 작성해줘.

[요구사항]
{요구}

[테스트 기준]
- 정상 케이스 3개
- 경계값 2개
- 예외 케이스 2개

[출력 순서]
1) 구현 코드
2) 테스트 코드
3) 실행 방법
```

### 템플릿 8. SQL 쿼리 작성
```text
다음 조건을 만족하는 SQL을 작성해줘.

[스키마]
{테이블/컬럼}

[요구]
{요구}

[출력]
- 최종 SQL
- 인덱스 추천
- 실행계획에서 확인할 포인트
```

## 3) 디버깅(Debugging) 템플릿

### 템플릿 9. 에러 원인 추적
```text
다음 에러를 단계적으로 디버깅해줘.

[에러 로그]
{로그}

[관련 코드]
{코드}

[요청]
1) 가능한 원인 우선순위
2) 각 원인 검증 방법
3) 가장 가능성 높은 수정안
4) 재발 방지 체크리스트
```

### 템플릿 10. 재현 시나리오 생성
```text
아래 버그를 재현 가능한 시나리오로 만들어줘.

[버그 설명]
{설명}

[출력]
- 환경 조건
- 재현 단계(step-by-step)
- 기대 결과 vs 실제 결과
- 재현 성공 판단 기준
```

### 템플릿 11. 로그 기반 분석
```text
아래 로그 묶음을 분석해서 병목/오류 패턴을 찾아줘.

[로그]
{로그}

[요청]
- 이상 징후 3가지
- 추정 원인
- 바로 적용 가능한 개선 3가지
- 추가로 수집할 로그 항목
```

### 템플릿 12. 성능 이슈 진단
```text
아래 코드의 성능 이슈를 진단해줘.

[코드]
{코드}

[맥락]
- 데이터 크기: {규모}
- 현재 응답시간: {ms}
- 목표 응답시간: {ms}

[출력]
- 병목 지점
- 개선안(난이도/효과)
- 빠른 임시해결책 1개
```

## 4) 리팩터링(Refactoring) 템플릿

### 템플릿 13. 가독성 리팩터링
```text
아래 코드를 동작 유지한 채 가독성 중심으로 리팩터링해줘.

[코드]
{코드}

[원칙]
- 함수 길이 축소
- 네이밍 개선
- 중복 제거
- 주석 최소화(코드 자체로 설명)

변경 이유를 항목별로 짧게 설명.
```

### 템플릿 14. 아키텍처 분리
```text
현재 모놀리식 구조를 레이어드 구조로 분리하는 계획을 제안해줘.

[현재 구조]
{설명}

[원하는 구조]
- controller
- service
- repository

[출력]
- 단계별 이전 계획
- 위험 요소
- 롤백 전략
```

### 템플릿 15. 레거시 코드 안전 개선
```text
레거시 코드를 큰 변경 없이 안정성 위주로 개선해줘.

[코드]
{코드}

[요청]
- null/예외 처리 강화
- 입력 검증 추가
- 로그 포인트 제안
- 기존 동작 영향 최소화
```

### 템플릿 16. 중복 로직 통합
```text
아래 두 코드의 중복을 공통 모듈로 통합해줘.

[코드 A]
{A}

[코드 B]
{B}

[출력]
- 공통화 전략
- 통합 코드
- 마이그레이션 순서
```

## 5) 문서화(Documentation) 템플릿

### 템플릿 17. README 초안
```text
다음 프로젝트의 README를 작성해줘.

[프로젝트 정보]
{정보}

[반드시 포함]
- 프로젝트 개요
- 설치 방법
- 실행 방법
- 환경변수
- 테스트 방법
- 트러블슈팅
```

### 템플릿 18. 코드 설명 문서
```text
아래 코드의 동작을 신규 팀원이 이해할 수 있게 설명해줘.

[코드]
{코드}

[출력]
- 전체 흐름
- 핵심 함수별 역할
- 입력/출력
- 주의할 포인트
```

### 템플릿 19. 변경 이력(릴리즈 노트)
```text
아래 변경사항으로 릴리즈 노트를 작성해줘.

[변경사항]
{목록}

[형식]
- Added
- Changed
- Fixed
- Breaking Changes
- Migration Guide
```

### 템플릿 20. 운영 핸드오버 문서
```text
서비스 운영 인수인계 문서를 작성해줘.

[서비스 정보]
{정보}

[포함 항목]
- 아키텍처 요약
- 배포 절차
- 장애 대응 절차
- 모니터링 지표/알람
- 자주 발생하는 이슈와 해결법
```

## 잘 안 되는 케이스 (왜 실패하나?)

1) **요구가 너무 추상적일 때**  
“좋은 코드 짜줘” 같은 요청은 결과도 추상적이다.

2) **입력 맥락이 비어 있을 때**  
기존 코드, 에러 로그, 실행 환경이 없으면 추측성 답변이 늘어난다.

3) **출력 형식을 안 정할 때**  
원하는 건 diff인데 장문 설명만 받는 식으로 어긋난다.

4) **제약 조건을 안 줄 때**  
라이브러리 제한, 성능 목표, 호환 버전이 없으면 실전에 못 쓰는 코드가 나오기 쉽다.

## 개선 팁 (품질을 올리는 한 끗)

- **한 번에 하나의 목표**: 구현/디버깅/리팩터링을 섞지 말고 분리해서 요청.
- **입력은 사실 위주**: 로그, 코드, 재현 단계 같은 증거를 붙이기.
- **출력 템플릿 고정**: 팀에서 공통 프롬프트 포맷을 정해 재사용.
- **검증 루프 추가**: “테스트 케이스 7개 생성”처럼 결과 검증 단계를 포함.
- **짧게 반복**: 큰 요청 1번보다 작은 요청 3번이 정확도와 생산성이 높다.

---

정리하면, Claude Code 프롬프트는 “말 잘하는 기술”이 아니라 “일을 잘 쪼개는 기술”에 가깝다.  
위 20개를 그대로 복붙해서 시작하고, 팀 상황에 맞게 조금씩 커스터마이징해보자.  
**AI 코딩 생산성은 프롬프트 품질에서 시작된다.**
